Why some languages make data immutable by default, and what it costs

22 November 2026 3 min read computing/languages

In short

Clojure, OCaml, Erlang and Rust all make some or all data immutable by default, for two linked reasons: a value nobody can change is safe to share between threads, and it is easier to reason about. The price is allocation on every update, logarithmic instead of constant-time writes, and a second set of escape hatches that each language ends up shipping.

Why the default flips

The default is an argument about where bugs come from. Clojure's rationale lists "defaults to immutability" as a design goal and gives the reason plainly: if a data structure can be mutated, it is dangerous to assume it won't be, and mutable stateful objects are hard to understand, test and reason about — a "concurrency disaster" [1]. Immutability makes sharing free, because a value handed to another thread cannot change underneath it, so the lock disappears along with the hazard [1].

A second, quieter motive is value semantics. Clojure's collections are persistent: an "update" returns a new collection that shares most of its structure with the old one, and old versions stay valid [2]. Vector and map access take O(log32 n) hops rather than O(1), but equality, hashing and caching behave predictably because the value never moves [2].

Rust starts somewhere else. let x = 5; cannot be reassigned; the compiler rejects a second assignment and suggests mut [4]. The stated aim is safety and easy concurrency, not purity: immutability is a promise the compiler checks for you [4].

It is not one claim

The phrase hides real differences. In OCaml, bindings and records are immutable by default, while arrays and ref are mutable and individual record fields opt in with mutable [6]. In Rust, mut is a property of the binding, not of the value [4]. In Clojure there is no assignment at all [1]. So "immutable by default" can mean mutation is impossible, mutation is possible but marked, or the compiler simply asks first — and only the first case forces the runtime to work hard to make updates cheap.

What it costs

Every persistent update allocates the nodes on the path it touches; nothing is overwritten in place. Clojure's own documentation concedes the point: "you simply can't get as fast using only pure functions and immutable data" [3]. The same page benchmarks building a one-million-element vector with conj at 8.4 ms and with the transient conj! at 5.5 ms on Java 25 and Clojure 1.12 — a micro-benchmark, but an honest one [3]. Transients exist because copying into a mutable structure and back "involves O(n) copying" [3].

The sharper cost is asymptotic. Balanced persistent trees give O(log n) update [2], but a linked list gives nothing away: ++ copies its left argument, so appending at the tail of a growing list costs O(n) per step and O(n²) overall [5].

%% quadratic: each step copies the whole accumulator
bad(0, _A, _B, Fibs) -> Fibs;
bad(N, A, B, Fibs) -> bad(N - 1, B, A + B, Fibs ++ [A]).

%% linear: prepend, then reverse once at the end
good(0, _A, _B, Fibs) -> lists:reverse(Fibs);
good(N, A, B, Fibs) -> good(N - 1, B, A + B, [A | Fibs]).

That is the Erlang efficiency guide's example, trimmed to the two clauses that differ [5]. The third cost is conceptual surface. Transients must be thread-isolated, cannot be aliased, and throw if used after persistent! [3]. OCaml's mutable fields and ref are a separate, imperative corner of the language [6]. You pay for the default twice: once at runtime, and once in the rules you must learn to step outside it.

Working with the default

Treat the default as a bet about which errors hurt more, then check the bet against the workload:

  • Data that crosses threads or task boundaries: keep it immutable and copy at the edges.
  • Tight build-up loops: mutate locally and publish an immutable value at the end — the transient pattern [3].
  • Look for tail appends (++, @, repeated concatenation) inside loops; that is where linear code turns quadratic [5][6].
  • Measure before rewriting. The Clojure gap above is roughly 1.5×, on one VM, for one operation [3].
