B-tree vs binary search tree: where the difference actually shows up

22 November 2026 3 min read computing/data-structures

In short

A binary search tree stores one key and two child pointers per node, so its height grows as log2 n. A B-tree packs many keys and children into one node, so its height grows as logb n. For a million keys that is roughly twenty node visits against three, and it changes insert cost, memory use and range scans as well.

One key per node, or hundreds

A binary search tree node holds one key and at most two children, with smaller keys left and larger keys right [2]. A B-tree node holds an ordered array of keys and, for a node with k keys, k+1 subtree pointers; the keys separate the subtrees [1]. In Knuth's definition a B-tree of order m has at most m children per node and all leaves at the same level, so it is balanced by construction rather than by rotations [1].

The consequence is height. A binary search tree needs about log2 n comparisons — 20 for a million keys — and an unbalanced one degenerates into a linked list with O(n) search [1][2]. A B-tree needs about logb n node visits, where b is the blocking factor; the same million-key example at b = 100 gives 3 reads [1]. PostgreSQL's index is the B+ shape: leaf pages hold tuples pointing at table rows, internal pages only downlinks, and "typically, over 99% of all pages are leaf pages" [3]. SQLite uses two variants: table b-trees keep all data in the leaves, index b-trees keep none [4].

Height is not the point; block reads are

Both structures do O(log n) comparisons; the difference is what one step costs. A B-tree node is sized to a storage block — b is chosen so that a node fits in one block, so an operation costs the number of nodes touched [5]. SQLite pages are powers of two from 512 to 65536 bytes, and every read or write starts on a page boundary [4]. A binary search tree has no such unit: each of its ~20 steps follows a pointer to an arbitrary address, a seek on disk and often a cache miss in memory [1].

Arithmetic shows the gap. On a 4096-byte page with an 8-byte key and a 4-byte child pointer, about 12 bytes per interior entry means roughly 340 entries per page. Two levels address some 116,000 keys; three address about 39 million. A million keys therefore sit three levels deep, against 20. Real fanout is lower — keys vary in length and leaves hold row pointers [3][4] — but the order of magnitude survives.

Updates differ too, and here the sources pull apart. A B-tree insert splits a full node and pushes the middle key to the parent, possibly all the way to a new root [1]; PostgreSQL describes splits cascading upward recursively [3]. Splits are amortised to a constant per insert, but each moves up to b keys, so Open Data Structures says that in the word-RAM model "adding a value to a B-tree can be much slower than adding into a balanced binary search tree" [5]. The B-tree article counters that fanout still wins in memory because of CPU caches [1]. Both hold: fewer levels means fewer misses, bigger splits mean more copying. Space is the other price — non-root B-tree nodes are only guaranteed to be half full [1].

Choosing between them

Choose by storage, not by asymptotics:

  • Pages or disk. B-tree or B+ tree; one node read per level is the design goal [1][3].
  • One process's heap, constant comparison. A balanced BST is a reasonable default. Linux tracks VMAs, timers and epoll entries in red-black trees [6].
  • Ordered scans. B+ trees link pages at each level, so a range scan walks leaves instead of re-descending from the root per key [1][3].
  • Comparisons only. Do not expect a B-tree win; its per-node binary search and key-shuffling splits can lose to a red-black tree [5].

One caveat: "order" and "leaf" are used inconsistently — an order-3 B-tree may mean six keys or seven [1]. Check the definition before comparing implementations.
