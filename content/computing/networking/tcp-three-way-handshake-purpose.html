Why TCP needs a three-way handshake instead of two

22 November 2026 3 min read computing/networking

In short

TCP's third message is not a formality. Without it the server cannot confirm that the client received its initial sequence number, and it cannot distinguish a fresh connection request from a delayed copy of an old one. The price is one round trip before any data flows.

What the third message establishes

RFC 9293 splits connection setup into four logical statements: A sends its initial sequence number (ISN) X; B acknowledges X; B sends its ISN Y; A acknowledges Y [1]. The middle two share a single segment, the SYN-ACK, so four statements fit in three messages [1].

A -> B   SYN      seq=1000
B -> A   SYN-ACK  seq=7000, ack=1001
A -> B   ACK      seq=1001, ack=7001

The numbers follow Dordal's worked example; a SYN occupies one sequence number, so a SYN is acknowledged with ISN+1 [3].

The asymmetry is the point. The SYN-ACK's acknowledgment field tells A that B received X, but a two-message exchange never tells B that A received Y. A two-message design would have to treat the connection as open at that point, on the strength of a segment it cannot confirm was delivered. In TCP as specified, a lost SYN-ACK leaves B waiting in SYN-RECEIVED while A retransmits or gives up [3]. Dordal says the third message "is an acknowledgment that the server side's SYN response was received correctly"; ESTABLISHED means both sides have confirmed each other's ISNs [3].

RFC 793 agrees more tersely: the procedure "involves an exchange of three messages", and a connection becomes established "when sequence numbers have been synchronized in both directions" [2].

Old duplicates and phantom connections

Sequence numbers alone do not make two messages impossible: the confirmation could ride on the first data segment, and TCP does allow data in the third segment [3]. It still has to arrive before the server commits. The harder problem is knowing which connection a segment belongs to.

TCP identifies a connection by its socket pair, and pairs are reused, so a SYN from an earlier incarnation can still be in the network. RFC 9293 calls this "the principal reason for the three-way handshake": "to prevent old duplicate connection initiations from causing confusion" [1].

The recovery path shows how the third message earns its keep. A opens a connection with ISN 100; an old duplicate SYN with ISN 90 then reaches B. B cannot tell it is old — the receiver has no way to know unless it remembers the last sequence number used, which is not always possible — so it replies normally, acknowledging 91 [1]. A is in SYN-SENT expecting an acknowledgment of 101, so it sends a reset with sequence number 91, and B returns to LISTEN [1]. The third segment turns a wrong guess into a reset, not a phantom connection.

With two messages, B would commit state to a connection A never opened and wait for a timeout to clear it. That is why SYN floods are cheap to send and expensive to serve: each unverified SYN can make the server allocate state [3]. Three messages do not prove agreement — RFC 9293 concedes that the receiver cannot always tell — but they let each side detect disagreement and abort.

The cost, and attempts to avoid it

The handshake costs a full round trip before data, which matters for short transfers [3]. TCP Fast Open is the Experimental extension that tries to buy that round trip back: it carries data in the SYN and SYN-ACK and "saves up to one full round-trip time" [4]. It does not repeal the reason for the handshake; it accepts the risk. Data in a SYN can be replayed if the SYN is duplicated, so an application that cannot tolerate receiving the same SYN data twice "MUST NOT enable TFO", and implementations must not enable it by default [4].

Three practical consequences:

  • In a capture, the third packet's acknowledgment should be the server's ISN plus one; a SYN-ACK with no ACK behind it is an unfinished handshake, not an open connection [3].
  • On a server, the window between SYN-ACK and ACK is where state is held, which SYN cookies and SYN caches are designed to defend [4].
  • For latency, reuse connections first — RFC 7413 recommends it — and reserve TFO for replay-tolerant requests [4].
