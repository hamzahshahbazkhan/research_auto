What a write-ahead log solves, and what it costs

22 November 2026 3 min read computing/databases

In short

A write-ahead log turns a commit into a sequential append plus one flush, not a scatter of page writes a power cut can tear. That buys atomicity and durability without flushing every dirty page at commit time. The bill is duplicated writes, a flush on the commit path, and checkpointing.

The problem: a commit is not one write

WAL is a family of techniques for atomicity and durability: changes are logged to stable storage before they reach the database files [1]. A transaction touches several pages in several files, and hardware cannot switch them all at once. Storage is written in sectors, and SQLite's notes assume a sector write is linear but not atomic: a failure in the middle can leave one page holding old and new bytes mixed [2]. There is no primitive for "all twenty pages or none".

Without a log, the only way to keep the promise is to force every modified page to stable storage before acknowledging. That means random writes and flushes, and SQLite says those flushes take up most of the time needed to complete a commit [2]. Crash midway and you cannot tell which pages landed, and the old contents are gone.

What the log buys: one append, then replay

The commit point becomes the durable log record, and dirty pages can be written whenever convenient. Recovery replays from the last checkpoint, redoing committed work and undoing the rest [1][2]. The log is append-only and sequential, so one flush of one file replaces a scatter of page flushes; PostgreSQL notes that only the WAL file must be flushed to commit, and that syncing it sequentially is cheaper than flushing data pages [3]. When many small transactions commit together, one flush can cover all of them [3]; commit_delay widens that window deliberately [5].

Take a transaction that updates six table pages and fourteen index pages. Without a log, all twenty random writes must be durable before the client hears "committed". With one, a single record is appended and flushed, the twenty writes follow in checkpoint order, and a crash in between is repaired by replay. The bytes written rose, but the wait collapsed.

The bill: twice the bytes and a flush

First, volume: every change lands in the log now and in the data file at the next checkpoint. SQLite notes a WAL write transaction writes page content once per commit, against twice for a rollback journal [4], but the page is copied back later, so the duplication is deferred, not avoided. PostgreSQL's full_page_writes adds the whole page image on the first change after each checkpoint, because an interrupted page write can be half old and half new; the docs call it "increasing the amount of data that must be written to WAL" [5].

Latency is the second. Synchronous commit waits for the flush, which for short transactions is "a major component of the total transaction time" [6]. synchronous_commit=off returns before the flush, losing at most three times wal_writer_delay of recent transactions — about 600 ms at the 200 ms default — without inconsistency [5][6]. Turning off fsync is worse: it risks unrecoverable corruption [5].

Housekeeping is the third. WAL grows until a checkpoint, so it costs disk and attention. max_wal_size defaults to 1 GB as a soft limit, and raising it lengthens crash recovery [5]. SQLite checkpoints near 1000 pages and warns that checkpoints need syncs and extra seeking, that readers slow as the WAL grows, and that one long-lived reader can block a checkpoint, letting the file grow without bound [4].

The knobs:

  • synchronous_commit: on pays a flush per commit; off trades recent transactions for speed [5][6].
  • checkpoint_timeout and max_wal_size: longer means less full-page WAL, slower recovery [5].
  • PRAGMA synchronous=NORMAL: no per-commit sync; the checkpoint is the only barrier [4].
